# Sanctuary Pergolas: The First Design Conversation

## Experimental Mobile Homepage Handoff Brief

Repository: `velt-design/sanctuary`  
Prototype route: `/home-experimental`  
Primary application: `apps/marketing`  
Status: Experimental prototype brief  
Primary viewport: Mobile  
Production homepage: Must remain unchanged during prototype development

---

## 1. Purpose

Create a mobile-first experimental homepage that behaves like the beginning of a Sanctuary design conversation rather than a conventional marketing page.

The experience should help a visitor quickly:

1. identify the kind of project they are considering
2. clarify what they want the space to achieve
3. see completed Sanctuary projects relevant to those priorities
4. understand what Sanctuary can assess next
5. begin a more informed and better-qualified enquiry

The concept should feel visually led, architecturally credible and commercially useful. It should not become a quiz, product configurator or automated design recommendation tool.

---

## 2. Strategic objective

The current homepage already explains Sanctuary clearly and provides strong project evidence. This prototype should test whether a more guided, project-led homepage can improve:

- first-screen comprehension
- emotional engagement
- relevant project discovery
- understanding of Sanctuary's bespoke design approach
- qualified enquiry starts
- project and design context carried into enquiry
- perceived architectural authority
- differentiation from standard pergola and construction websites

The prototype should test a substantially different information architecture, not merely restyle existing sections.

---

## 3. Central concept

The homepage opens with a real completed project, then asks the visitor a small number of practical, visual questions.

Each answer changes the project evidence and next step shown to the visitor.

The interaction should feel like this:

> Show us what you are trying to create.  
> We will show you relevant built work and what information would help us assess it.

The experience should remain restrained. It should feel like an architectural design conversation, not a consumer product selector.

---

## 4. Core principles

### 4.1 Start with intended outcome

Do not ask the visitor to choose a roof form or product before they understand what they need.

Questions should focus on:

- intended use
- site or project context
- desired environmental outcome
- available project information

### 4.2 Use projects as the main proof mechanism

Every pathway should be supported by real completed Sanctuary projects.

Do not create abstract recommendations without built evidence.

### 4.3 Keep the decision burden low

Use a maximum of three questions.

Each question should have three or four clearly differentiated answers.

The visitor must always be able to:

- go back
- change an answer
- skip the guided flow
- browse all projects
- start a general enquiry

### 4.4 Avoid false precision

The prototype must not claim to:

- determine the correct pergola form
- confirm structural feasibility
- confirm consent requirements
- calculate price
- determine roof material suitability
- replace a site assessment
- generate a final design

Use language such as:

- relevant examples
- useful starting point
- projects with similar priorities
- information that would help Sanctuary assess the site
- an initial project conversation

Avoid language such as:

- perfect match
- recommended design
- best roof for your site
- guaranteed solution
- instant design

### 4.5 Preserve one responsive website

Use shared project data, shared content and existing routes.

Do not create a separate mobile site or duplicate project records.

### 4.6 Keep the work visually led

The visitor should understand the pathway mainly through:

- project photography
- short labels
- clear choices
- project metadata
- concise design observations

Text should support the visual experience, not dominate it.

## 5. Prototype information architecture

The experimental homepage should contain six primary acts.

### Act 1: Project-led opening

Open with one completed Sanctuary project.

Default lead project:

- Warkworth Outdoor Room

The first viewport should include:

- full-bleed project image
- Sanctuary Pergolas identity through the existing header
- project name
- location
- roof form or project type
- concise company proposition
- primary action: `Start with your project`
- secondary action: `Explore the Warkworth project`

Suggested proposition:

> Bespoke fixed-roof pergolas designed around the home, the site and how the space will be used.

The project should feel like the opening of an architectural portfolio, not a decorative hero background.

### Act 2: First question, project context

Question:

> What are you trying to create?

Initial answer set:

1. `Cover an outdoor area at home`
2. `Create a more complete outdoor room`
3. `Resolve a commercial or professional project`

Each answer should:

- update the active project image or project set
- update a short supporting statement
- establish the enquiry audience
- determine the next question

Suggested pathway mapping:

#### Cover an outdoor area at home

Possible projects:

- Dairy Flat Estate
- Mt Maunganui Box
- St Heliers Townhouse
- Tindalls Bay Pavilion

#### Create a more complete outdoor room

Possible projects:

- Warkworth Outdoor Room
- Riverhead Gable Pavilion
- Tindalls Bay Pavilion

#### Resolve a commercial or professional project

Possible projects:

- The Good Home commercial terrace
- Atelier Shu Cafe
- Velskov Forest
- other suitable commercial examples from shared project data

### Act 3: Second question, desired result

Question:

> What matters most for the space?

Initial answer set:

1. `Retaining daylight`
2. `Gaining deeper shelter`
3. `Integrating with difficult architecture`
4. `Adding ceiling, lighting or enclosure`

Each answer should update:

- the active supporting project
- a short design observation
- the available matched projects
- the contextual enquiry summary

Suggested priority mapping:

#### Retaining daylight

Relevant attributes:

- acrylic roof
- opal or clear roof zones
- combination roofing
- retained interior daylight
- lighter roof treatment

#### Gaining deeper shelter

Relevant attributes:

- solid roof zones
- deeper coverage
- more complete roof treatment
- blinds or edge protection where applicable
- sheltered outdoor room

#### Integrating with difficult architecture

Relevant attributes:

- attached or freestanding response
- complex junctions
- unusual geometry
- difficult roofline
- level perimeter
- site-specific connection strategy

#### Adding ceiling, lighting or enclosure

Relevant attributes:

- cedar or timber lining
- solid ceiling
- lighting
- heating
- screens
- blinds
- fireplace or more complete room treatment

### Act 4: Third question, project readiness

Question:

> What information do you already have?

Initial answer set:

1. `Site photos`
2. `Rough dimensions`
3. `Plans or drawings`
4. `An early idea only`

This question should not change the architectural recommendation.

It should change:

- what Sanctuary asks for next
- the wording of the enquiry action
- the guidance shown before contact
- the project brief summary passed into enquiry

Example response:

> Photos and approximate dimensions are enough for Sanctuary to begin an initial review. Plans can be added where available.

For `An early idea only`:

> You can begin with the suburb, intended use and a few photographs. Sanctuary can identify the useful questions from there.

### Act 5: Matched projects

Show two matched projects based on the first two answers.

Each project should display:

- project image
- project name
- location
- project type
- roof form
- one sentence explaining why it is relevant
- `View project`
- `Use as a reference`

Do not label either project as the correct solution.

Suggested heading:

> Relevant built examples

Suggested supporting copy:

> These projects share some of the priorities you selected. Your site, dimensions, exposure and connections will still determine the right response.

### Act 6: Contextual enquiry handoff

The final section should summarise the visitor's selections.

Example:

> You are considering a residential outdoor room where deeper shelter and integrated lighting matter. You currently have site photos.

Show:

- selected project context
- intended outcome
- primary priority
- information already available
- useful next inputs
- live review proof
- direct enquiry action
- alternative phone or email route if already present in the shared contact experience

Primary action examples:

- `Share your site photos`
- `Start your outdoor room brief`
- `Send your plans and project details`
- `Discuss the commercial project`

The action must use the existing contact route and preserve validated context.

## 6. Recommended interaction model

### 6.1 One continuous page

The concept should remain a normal vertically scrolling homepage.

Do not use:

- full-screen modal steps
- route changes between questions
- mandatory scroll snapping
- scroll locking
- horizontal swipe as primary navigation

### 6.2 Progressive guided state

Each answer should reveal the next step beneath the current one.

The active project image may change, but the visitor should remain spatially oriented.

Recommended behaviour:

1. select an answer
2. transition the supporting project image and observation
3. reveal the next question
4. move focus or scroll only when user initiated and helpful
5. preserve previous answers visibly as compact editable selections

### 6.3 Editability

After answering, show a concise summary pill or row.

Example:

- `Project: Outdoor room`
- `Priority: Deeper shelter`
- `Information: Site photos`

Each must include a visible `Change` action.

### 6.4 Direct escape routes

At every stage, retain:

- `Browse completed projects`
- `Start a general enquiry`

The guided flow should help visitors, not trap them.

## 7. Project matching model

Use deterministic, transparent matching.

Do not introduce machine learning or external recommendation services.

### 7.1 Data source

Use the existing shared project data from:

`apps/marketing/data/projects.ts`

Relevant fields may include:

- `slug`
- `title`
- `location`
- `type`
- `roof`
- `configuration`
- `roofApproach`
- `materials`
- `tags`
- `constraint`
- `stats`
- `gallery`
- `related`

### 7.2 Matching configuration

Create a small typed configuration file specifically for the prototype.

Suggested path:

`apps/marketing/app/home-experimental/matching.ts`

Example structure:

```ts
type ProjectIntent =
  | 'home-cover'
  | 'outdoor-room'
  | 'commercial-professional';

type DesignPriority =
  | 'daylight'
  | 'shelter'
  | 'complex-architecture'
  | 'integrated-comfort';

type Readiness =
  | 'photos'
  | 'dimensions'
  | 'drawings'
  | 'early-idea';

type MatchRule = {
  intent: ProjectIntent;
  priority: DesignPriority;
  projectSlugs: [string, string];
  rationale: string;
};
```

The mapping should be editorially controlled.

Do not calculate matches from loosely weighted tags during the first prototype.

### 7.3 Matching behaviour

- return exactly two project matches
- avoid returning the same project twice
- use a reliable default if a configured project is unavailable
- allow the visitor to choose either project as the enquiry reference
- allow browsing the complete projects route
- store no sensitive personal information

## 8. Enquiry context

Use the existing `buildEnquiryHref` and contact context system.

At minimum, preserve:

- `enquiry_type`
- `source_path`
- `source_component`
- `source_project`

Recommended extension for the experimental prototype:

- `design_priority`
- `project_intent`
- `project_readiness`

Any new values must be:

- strictly validated
- limited to known enums
- length constrained
- ignored safely when invalid
- carried into analytics and enquiry payloads only where appropriate

Do not pass arbitrary visitor-entered text in the URL.

If extending the shared enquiry context is considered too broad for the first prototype, keep the additional state in `sessionStorage` and pass only the supported audience and project context into contact.

Preferred approach:

1. use supported context for audience and selected project
2. store prototype selections in session storage
3. display a concise summary on contact where technically safe
4. include validated selections in the final enquiry payload
5. avoid changing unrelated routes

## 10. Visual direction

### 10.1 Overall character

The prototype should feel:

- architectural
- editorial
- calm
- precise
- tactile
- visually led
- premium without luxury cliches
- contemporary without looking like a technology product

### 10.2 Photography

Use existing project photography.

Prioritise:

- images that clearly show the relationship to the home
- occupied spaces
- roof, ceiling or glazing details
- visibly different project conditions
- strong mobile crops

Avoid:

- generic lifestyle crops
- repeated use of the same image
- overly dark images beneath heavy overlays
- images that do not explain the selected priority

### 10.3 Layout rhythm

Use varied but controlled moments:

- full-height opening
- image with compact choice overlay
- project response split
- concise question block
- two matched project chapters
- focused enquiry close

Avoid repeating the same card grid for every stage.

### 10.4 Motion

Use motion only to clarify state changes.

Recommended:

- restrained image crossfade
- small caption transition
- controlled reveal of the next question
- subtle progress movement
- no parallax required

Avoid:

- autoplay video
- continuous ambient motion
- text flying into view
- exaggerated easing
- looping effects
- motion on every scroll event

### 10.5 Architectural drawing language

A minimal datum line, project number or section marker may be used to connect the experience.

Do not add decorative technical drawings unless they are based on real architectural logic and improve understanding.

## 12. Accessibility requirements

Meet WCAG 2.2 AA.

Required:

- one logical document order
- semantic headings
- real buttons for answer selections
- radio group semantics where choices are mutually exclusive
- visible legends or accessible question labels
- minimum 44 by 44 pixel interactive targets
- clear selected states beyond colour alone
- keyboard operation for all controls
- visible focus styles
- no gesture-only controls
- no mandatory scroll snapping
- no automatic focus movement that disorients the visitor
- accurate alt text for every project image
- decorative images marked appropriately
- reduced-motion support
- readable overlay contrast
- no hidden essential content
- screen-reader announcement only for meaningful result changes
- page remains understandable without JavaScript

The no-JavaScript version should show:

1. project-led opening
2. all three intent pathways as standard links or sections
3. representative projects for each pathway
4. direct enquiry
5. proof and reviews

---

## 13. Performance budget

Target mobile performance:

- LCP: 2.5 seconds or less
- CLS: below 0.05
- INP: below 200 milliseconds
- additional route JavaScript: 55 KB gzip or less
- first-viewport image: 320 KB or less at 430 px, DPR 2
- eager images: maximum two
- new runtime dependencies: zero
- autoplay media: none
- continuous animation loops: none

Implementation guidance:

- use `next/image`
- use accurate `sizes`
- preserve fixed image aspect ratios
- lazy-load all non-critical projects
- preload only the opening image
- use `IntersectionObserver` rather than continuous scroll handlers
- avoid client-side image swapping before hydration
- avoid rendering all project gallery images at once
- use CSS transitions where possible
- use `content-visibility` for suitable lower-page sections
- test on a mid-range Android profile, not only desktop emulation

## 18. Acceptance criteria

The prototype is complete when all of the following are true.

### Experience

- the first viewport opens on a real completed project
- Sanctuary's fixed-roof design-and-build service is understandable within the first screen
- the guided experience contains no more than three questions
- every question is visually and verbally clear
- each pathway presents relevant completed projects
- the visitor can select one project as a reference
- the visitor can skip the guided flow
- the visitor can change previous answers
- the final enquiry action reflects the selected context
- the experience feels complete without reading long explanatory sections

### Technical

- `/` remains unchanged
- `/home-experimental` is noindex
- shared project data is reused
- project records are not duplicated
- client-side code is limited to interactive components
- no new runtime dependency is added
- enquiry context is validated
- invalid state falls back safely
- no hydration errors occur
- no horizontal overflow occurs
- all required widths pass
- desktop stability checks pass

### Accessibility

- all controls are keyboard operable
- answer groups use appropriate semantics
- selected states are clear without colour
- focus remains visible
- reduced-motion mode is supported
- essential information is not motion dependent
- no gesture is required
- no serious or critical automated accessibility issues remain
- no-JavaScript fallback remains usable

### Performance

- LCP is 2.5 seconds or less
- CLS is below 0.05
- INP is below 200 milliseconds
- additional JavaScript remains within 55 KB gzip
- opening mobile image remains within the defined budget
- no unnecessary eager images are loaded
- no continuous animation loop runs

### Analytics

- all prototype events are consent aware
- events fire once
- selected intent, priority, readiness and project are captured
- prototype traffic is distinguishable from the current homepage
- contact submissions retain supported context

## 19. Prototype success measures

The prototype should be considered promising if it demonstrates:

- stronger five-second understanding than the current homepage
- meaningful interaction with the first question
- increased relevant project exploration
- project-reference selection
- contextual enquiry starts
- no decline in overall enquiry completion
- positive qualitative feedback on clarity and premium perception
- no material performance or accessibility regression

Suggested initial directional signals:

- at least 25 percent of engaged mobile visitors answer the first question
- at least 50 percent of those visitors complete all three questions
- matched project engagement exceeds the current selected-project interaction rate
- at least 10 percent of completing visitors select a project reference
- contextual enquiry starts outperform generic enquiry starts among engaged visitors

These are experiment signals, not permanent business targets.

---

## 20. First implementation priority

Begin with the smallest commercially meaningful version:

1. project-led opening
2. first question only
3. two project responses per answer
4. project-reference CTA
5. existing contact context
6. analytics

Do not build all three questions before confirming that visitors understand and use the first interaction.

The complete route and architecture may be prepared, but the first testable release should keep the active experience deliberately narrow.

---

## 21. Definition of done

The work is done when the experimental route provides a credible, testable alternative homepage experience that:

- begins with completed work
- asks useful project questions
- responds with relevant built evidence
- preserves a chosen project through to enquiry
- remains fast and accessible
- leaves the production homepage and desktop experience stable
- creates enough behavioural evidence to decide whether the concept should be expanded, revised or abandoned
