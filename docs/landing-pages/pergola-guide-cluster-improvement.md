# Pergola Guide Cluster Improvement

Status: implementation source for the July 2026 guide-cluster revision.

This document records the required pre-rewrite strategy for `/pergola-guides` and its ten linked pages. The supplied Sanctuary Pergolas Guide Cluster Improvement Brief remains the primary editorial source of truth. The [marketing claims register](../marketing-claims-register.md) governs any statement about price, timing, warranty, performance or the current product offer.

## Editorial ownership

| Page type | Owner pages | Purpose |

## `/pergola-guides`

1. **Target query and intent:** Pergola guides, pergola design guide Auckland; exploratory visitors who need to identify the decision in front of them.
2. **Page role:** The cluster index and progression owner. It classifies service, product and decision pages, and preserves the numbered sequence from 01 to 10.
3. **Competing pages:** Every child guide if the hub attempts to answer detailed design, cost, consent or product questions itself.
4. **Retain:** Three decision chapters, the architectural library presentation, short summaries and the complete ten-guide list.
5. **Remove or consolidate:** Remove any answer-level copy and keep chapter introductions focused on routing. Each number must appear once and in ascending order.
6. **Claims needing approval:** None. Do not introduce product, price, timing, warranty or performance claims in routing copy.
7. **Internal links:** Link all ten pages, show each page role, and provide a clear first-step recommendation for broad projects and complex sites.
8. **CTA:** Start with Pergolas Auckland for a general brief; use Custom Pergolas Auckland when site or connection constraints already define the problem.

## Implementation and verification rules

- Give every guide a visible breadcrumb and previous, hub and next progression.
- Use `Service` structured data only on service pages. The hub remains a `CollectionPage`; product and decision guides remain editorial `WebPage` content.
- Do not emit `FAQPage` schema as a rich-result tactic. Visible questions may remain where they are unique and useful.
- Keep one self-referencing canonical, one H1 and unique title and description on every page.
- Use project dimensions, site constraints and design responses only where supported by the typed project record. Do not use contradictory legacy project-section copy as evidence.
- Keep forms specific to the decision on the page. Preserve the existing enquiry API and attachment flow.
- Do not use em dashes in new or revised copy.
- Search Console query overlap, external index state and any historic PDF index state require production property access and cannot be proven locally.
