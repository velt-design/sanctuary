# Projects, Contacts, Estimates, And Calculator

This doc is the current-state reference for the core staff portal workflow before quotes, design requests, schedule, running jobs, and job packs. Use it when touching contacts, projects, project snapshots/tasks, calculator estimates, estimate versions, estimate locks, or local-first estimate mutations.

## Contact And Project Flow

Contacts and projects are staff-owned portal records. Marketing lead capture can create upstream enquiry data, but staff workflow state belongs in the portal.

- Contact create/update routes write `contacts` and return mapped contact shapes.
- The Contacts index renders its heading, actions, search, and truthful list region before any database read. `GET /api/staff/v1/contacts/index` then loads one bounded server-filtered/sorted page through the authenticated staff API and the user-owned QueryClient. Page sizes are 25/50/100, exact filtered counts and stable ordering come from `staff_contacts_index_v1()`, and the browser does not download or render the full contact table for ordinary list use. The client has explicit `pending`, `cached`, `fresh`, `refresh-failed`, and `unavailable` states: a response is shown only when its query/page identity matches the current request, known same-request rows remain visible during refresh or network/server failure, `401`/`403` hides them, and an empty state requires a fresh successful response.
- Contacts-index links update `/staff/contacts` immediately without the global route overlay and preload route/data only from hover, focus, touch, or pointer-down. The generic portal-index navigation owner preserves Projects filters, modified clicks, new tabs, and browser Back. Contact edits patch matching rows across cached list pages and linked-contact segments without treating a partial page as the complete canonical list. CSV import remains a separate route-owned lazy workflow boundary; this list migration does not redesign it.
- Contact Detail editing uses the user-owned local-first queue key `portal.contact.details.update`. Done closes immediately and keeps the desired values visible while the full normalized working copy persists through the authenticated contact API. Ordered drafts survive navigation, reload, and offline periods. Transient failures retain the desired values and retry; terminal validation/access/conflict responses restore the last confirmed contact across detail, Contacts index, canonical contact list, and Projects-index contact caches while retaining the rejected draft for Review/Retry. A successful handler accepts the server-mapped contact and clears only the matching working copy when no newer contact save remains.
- The Contacts workflow is a production UI-foundation consumer. Index/create/detail/import compose the shared page canvas, operational headers, controls, cards, responsive tables, truthful loading/data states, alerts, and focus-managed modal without moving the read, write, cache, lazy-boundary, or local-first owners above. At mobile widths, list tables retain identity and actions while hiding secondary columns, Contact Detail fields reflow in place, and header/breadcrumb actions preserve 44px targets. The CSV dialog traps focus, blocks close while importing, returns focus to the import trigger, and never submits during browser review evidence.
- `POST /api/staff/v1/projects` owns project creation. The browser submits one stable project command ID plus either an existing contact ID or one stable new-contact command. The server checks normalized exact email/phone duplicate candidates, then calls the transactional `project_create_v2` RPC, which creates the project, records its V2 model marker and Active state, and seeds the first-email obligation. Matching stable-ID replays return the committed identity; a different payload returns `PROJECT_CREATION_COMMAND_CONFLICT`. Missing V2 schema fails closed with no legacy fallback. This path is repository-local until `20260729_000002_project_work_items_v2.sql` is applied; existing projects are not backfilled.
- Contact/project detail routes continue to own their respective reads and updates. `GET /api/contacts/[contactId]` is the bounded authenticated lookup used to restore a preselected contact in the project-create combobox.
- The persistent portal content boundary renders the real header, actions, filters, and truthful "Updating projects" list frame synchronously on an ordinary Projects-index click, while keeping the sidebar available; the matching route loading boundary uses the same frame for direct route transitions. The page entrypoint does not await request search params or data; its client controller reads the current filters and date, then dismisses the pending frame after mounting. One authenticated React Query request to `GET /api/staff/v1/projects/index` loads one bounded server-filtered/sorted active/archived/all page plus only the linked contact display rows needed by that page through `staff_projects_index_v1()`.
- Projects-index reads have five states: `pending`, `cached`, `fresh`, `refresh-failed`, and `unavailable`. A response is usable only when archive, search, status, due-date, sort, page, and page-size identity match the current request, so one scope/filter cannot borrow another scope's rows. Known same-request rows remain visible during background refresh and network/server failure, while `401`/`403` hides them. An empty state is truthful only after a fresh successful response.
- Reversible Projects-index writes are optimistic through the current user's QueryClient. Name, phone, address, silent stage-correction, archive, and restore feedback appears before the API settles; only the affected field/state is rolled back on rejection, a small `Saving...` marker remains visible while syncing, and success language is emitted only after server confirmation. Archive moves update active/archived/all membership and known counts together. Hard delete remains server-confirmed and is never optimistic. The data-free project-mutation browser fixture mounts this production owner, deliberately delays persistence, and records feedback/useful/background timing separately; its disabled fixture query and intercepted sample request never read or write customer tables.
- Links to the Projects index update the canonical `/staff/projects` URL immediately, bypass the blocking route overlay, and preload route/data only on hover, focus, touch, or pointer-down. Fresh index results seed the established project/contact list keys so project opening remains instant; mutations patch or invalidate both combined and canonical caches.
- Project detail pages use the existing authenticated React Query request to `/api/projects/[projectId]/snapshot`; the server route renders the project shell without repeating that snapshot read.
- Project Details editing uses the user-owned local-first queue key `portal.project.details.update`. Done closes the editor and exposes the desired values immediately; full normalized drafts remain in the per-user working-copy store until the ordered authenticated API saves finish. Transient/offline failures retain the desired values and retry. Terminal validation, permission, not-found, lock, or conflict responses restore the last confirmed cache values while retaining the rejected working copy for Review/Retry; `401`/`403`/`404` also refresh the protected project read boundary. A confirmed save clears its working copy only when the stored draft still matches that queue item and no newer project-detail save is pending.
- V2 archive/restore is an admin-only versioned project-work command with a required reason. Archive cancels active work and clears compatibility projection; restore does not revive cancelled items. Existing unmarked projects retain the legacy archive route until reviewed migration.

## Project Snapshot, Pipeline, And Tasks

`ProjectPageSnapshot` is the complete project-detail read model for the staff project page. It combines project/contact data, pipeline and task state, email summaries, and notes. The access-defining project/contact row is read independently, while all subordinate relations are embedded in one second auth-bound PostgREST read. A subordinate-read failure rejects the complete snapshot so the client retains known data with Retry instead of presenting partial arrays as fresh.

Project opening has five explicit read states: `pending` for a direct link with no known summary, `summary` while authenticated summary fields are visible, `fresh` after the full snapshot arrives, `refresh-failed` when known data remains visible with Retry, and `unavailable` after a `401`, `403`, or `404` response. Access-ending responses must hide known project data. Debug exports are fresh-snapshot-only. The Projects list includes the lightweight project shell in its normal bundle and gives the rendered instant view to a tiny Projects-layout navigation boundary, which updates browser history and keeps the current-user cached summary visible while the existing authenticated snapshot query completes. On a direct link without list cache, `GET /api/staff/v1/projects/[projectId]/summary` supplies only the RLS-visible project/contact shell; the complete snapshot still refreshes through its existing query and key in parallel. The shell must not be hidden behind an intent-time dynamic import: a brief hover or direct click still needs immediate useful content. Browser Back clears that instant view and lets Next restore its own retained list route; server-rendered React nodes are never treated as a reusable cache. The persistent boundary makes browser Back reliable without importing project-opening code into Design Workbench.

Project rows preload the route and existing full-snapshot query on hover, keyboard focus, touch, or pointer-down. There is no automatic first-three-project fan-out. The activity-key Overview is the default workflow and a real lazy boundary; its local loading state appears only inside the already-usable project frame. Calculator, Commercial, and Job Packs are separate lazy code boundaries. One compact sticky project header owns identity, the inline project owner, the shared tab registry, and responsive project actions; contact and region details remain in Overview. Its first row contains only project name, the canonical current-stage badge, global search, owner, Projects, Design Workbench, and the permission-gated More action. Its second row contains only the shared tabs. The project ID/reference and nine-stage pipeline visual are not repeated in the header. Wide layouts use equal left and right tracks so global search stays on the header centreline; the search track narrows before the command row switches to scrolling. At narrow widths the first row becomes an internally scrollable command rail and the tab row retains its own keyboard/touch containment, preserving exactly two rows without document overflow or hidden commands. Interactive overlays inside that rail must escape its overflow boundary rather than weakening the row containment. Tab intent preloads exact code/data from hover, focus, touch, or pointer-down. On selection, the project frame owns an optimistic tab key shared by the header and body, so both the selected state and the matching useful shell render before `router.replace()` commits the canonical query string; Commercial independently applies the same rule between Quotes and Invoices. The canonical route remains authoritative and clears that optimistic state after commit, while workflow data settles inside the selected shell. The active workflow then occupies the full project-page width. Project details and stage correction live in Overview at every breakpoint; there is no side rail or responsive Details tab. Overview can load its independent command-centre read during the summary state, while its notes/tasks region remains explicitly updating until the full snapshot is ready and never turns placeholder empty arrays into a false empty state.

Project route compatibility remains deliberate: `tab=estimates` owns the embedded Calculator; `tab=quotes` and `tab=invoices` select the matching inner view of Commercial; `tab=job-packs` remains conditional; and retired `tab=emails` plus unknown values normalize to `tab=activity` while preserving unrelated query parameters. Commercial retains quote selection and creation context when switching inner views and clears only quote preview when entering Invoices.

- `workModel: "v2"` selects the central V2 work projection; an unmarked project stays `workModel: "legacy"` and keeps task definitions from `pipelineDefinition.ts` plus `project_task_checks`.
- Staff project creation reaches `project_create_v2` only through `POST /api/staff/v1/projects`; browser code has no direct project-table creation helper.
- V2 state, work-item, confirmation, archive, queue, receipt, and event mutations use the dedicated staff/admin command routes and versioned RPCs. A work-item completion completes only the item; it cannot send email, move stage, record payment, or mutate Design, quotes, invoices, Schedule, or Running Jobs.
- Legacy stage-task rows are filtered, read-only compatibility evidence in Overview. Call and Site Visit rows/actions/categories/links are hidden; a prohibited server-selected action renders `Legacy work needs review` and browser code never selects a replacement. Legacy task/manual-action/follow-up writers still reject V2 projects.
- Overview renders one `ProjectWorkSection` from the command-centre/snapshot work-model boundary for either V2 or clearly labelled legacy compatibility. There is no second Tasks card or V2 sidebar. Blocked work is an exception rather than an enabled primary action. `projectWorkCache.ts` is the only cache patch/invalidation module: `patchProjectCommandCentreCache` owns complete command-centre response patches, the V2 projection helper owns command-centre/snapshot/summary fan-out, and the shared invalidator refreshes project, Work Queue, and Dashboard reads. Controls pause whenever the owning read is refreshing, stale, refresh-failed, or disagrees with the other authoritative read about the work model.
- Site Visits stays out of global navigation and V2 work items never target it. While an active V2 project is in the Site Visit stage, Project Work controls expose one bounded **Book or confirm site visit** deep link to the retained direct workflow. That link resolves an existing visit across calendar weeks and opens it, or opens a create dialog already linked to the project when no visit exists. The optional `SITE_VISIT_COMPLETED` confirmation remains a separate manual fact with no task, stage, or Schedule side effect.
- When the current quote is accepted and the pipeline is still at Sent, the Overview commercial card exposes the authoritative **Record deposit received** action. The route requires an open deposit invoice backed by an accepted quote, then atomically records `deposit_paid_date` with the conditional Sent-to-Deposit transition before emitting the won lifecycle event. PostgreSQL records the first transition in immutable `projects.deposit_received_at`; a recent idempotent replay uses only that timestamp, while a legacy Deposit row without it fails closed. It is not modelled as a generic V2 work-item completion.
- Snapshot readiness comes from portal data such as booked site visits, generated estimates, accepted quotes, open deposit invoices, scheduled install items, and generated job packs.
- Stage action routes under `apps/portal/app/api/staff/v1/projects/[projectId]/action` own staff workflow side effects.
- Orientation, the single Project Work region, current design/commercial, and bounded recent notes/events are composed inside the activity-key Overview (`OverviewTab.tsx`). There is no separate Tasks panel.

The V2 compatibility projection writes the highest-ranked open item to `projects.next_action*` and `follow_up_date` for existing list/dashboard consumers and clears those fields for Waiting, Closed, or archived projects. It excludes blocked work and specialist actions and is never a reverse import. Do not hard-code duplicate pipeline, ranking, commercial, or lifecycle truth in components.

## Calculator And Estimate Versions

The calculator produces estimate snapshots. Estimate rows are versioned per project and hold calculator inputs, outputs, warnings, costing metadata, derived summary fields, and drawing/snapshot state.

- Estimate payload normalization lives in `apps/portal/lib/estimates/persistence.ts`.
- Estimate summary mapping lives in `apps/portal/lib/estimates/summarize.ts` and server mapping helpers.
- Version labels are derived from project estimate rows; new estimates advance the next available version.
- Estimate snapshots carry calculator inputs plus output sections such as `derived`, `projectSnapshot`, `snapshot`, and `configVersions`.
- Every create attempt carries a stable `clientIntentId`. The server replays an existing estimate for the same project/intent instead of creating another version, including recovery after a response is lost.
- A new estimate save must carry the exact calculator snapshot being approved. If that snapshot is absent and the intent is not a replay, the route returns a conflict and asks staff to recalculate; it must never substitute the project's latest saved estimate or another browser result.
- Live calculator responses carry the exact costing configuration provenance used by that calculation. Reprice/save copies it into `outputs.configVersions.costingControl`; it must not infer the version from a later metadata request because an admin could publish between calculation and save.
- Published provenance contains the immutable configuration version ID/number, content hash, and base manifest version. `estimates.costing_config_version_id` references that published row with restrictive deletion. Before the first publish, provenance contains the complete hashed effective legacy configuration snapshot and the foreign key remains null.
- Frozen estimate inputs and outputs remain the historical commercial record. Re-evaluation may load the immutable published version (or the legacy snapshot) through `resolveHistoricalCostingConfiguration`, but ordinary estimate reads, quotes, actual-cost comparison, invoices, and job packs must not silently reprice stored history.
- Calculator blind add-ons keep `widthMm` and `coverLengthMm` in saved estimate snapshots for compatibility, but the staff calculator presents and accepts those two dimensions in metres and converts them back to mm in the client adapter before pricing/persistence. A meaningful blind with invalid dimensions or selections is a quote blocker; quote mapping omits the invalid line and reports a blocking issue instead of silently creating a zero-dollar line.
- Drawing state can be stored inside estimate snapshot/drawing draft shapes, but design workbench architecture and compatibility rules are owned by `docs/design-workbench-architecture.md`.

The calculator workspace keeps workflow context and save readiness in a persistent command bar. At `/staff/calculator`, staff can search active projects by name, quote reference, or address; selecting one opens that project's calculator workflow and active draft while the scratch draft remains in local/session storage under its original key. The project-page wrapper fixes the Calculator to its current project, passes the existing host/cache identity and a typed design-navigation model into the workspace, removes the project picker, and renders the Calculator as an embedded section beneath the measured sticky masthead. Embedded mode folds design selection, editing/module context, browser-draft state, freshness, detail level, and Save into one compact command bar; it does not repeat the project name or Calculator heading. Historical, invalid, loading, and failed design states retain a minimal navigation row because the full Calculator command bar is not mounted there. The standalone Calculator retains its heading and project picker.

The mounted command bar uses one source, reading, visual, and focus sequence: project/design/draft/module identity, readiness, Basic, Advanced, then one Save. Responsive wrapping does not reorder that sequence. Readiness presentation derives a root-cause count, blocked-check count, and review count from the existing Quote Status rows without changing `hasStatusBlockers` or Save preflight. Input-caused Engine rows remain visible but say they are blocked by input issues; Updating and recalculation pending are waits for a current result, while an independent Engine error remains its own cause. The primary label uses singular/plural causal language such as `1 input issue blocks Save`, and Quote Status retains the complete check list plus its separate blocked-check count.

The Calculator is a UI-foundation consumer without replacing its specialist workflow owners. Its scoped legacy variables resolve through semantic foundation colour, border, focus, canvas, and density roles; preview warnings use the shared accessible alert pattern; and mobile command-bar controls meet the 44px touch target. This is presentation-only and does not move costing, geometry, draft, save, or handoff authority.

The project Calculator defaults to the active editable draft, or an explicit blank design (`newDesign=1`) when none exists. `estimateId` deep-links only to an editable active draft. Historical records are locked revision sources: selecting one shows an explicit locked-source state, and `Start revision` enters the existing `fromEstimateId` flow without mutating the source. Saving a blank design or revision creates a new estimate, then replaces `newDesign`/`fromEstimateId` with the saved `estimateId` without replaying the mutation. Per-design internal notes remain stored for compatibility but no longer have a project-page editing surface.

Calculator input drafts are protected separately from estimate Save. The command bar reports `Saving locally`, `Saved locally`, `Restored unsaved work`, or `Local save failed` for the browser working copy/session snapshot and always explains that Save is still required to update the estimate. Embedded mode keeps the short status visible and exposes the longer browser-draft explanation through its accessible description; local-save failures keep the explanation visibly expanded. Working-copy restoration takes priority over the session fallback, active-module selection restores with the inputs, and a draft-key change must not persist the previous project's values while an estimate or duplicated source is still loading. These states do not enqueue an estimate mutation and are separate from the post-Save `syncing`, `synced`, `offline`, `error`, and `conflict` states.

Multi-module calculator drafts use one canonical module navigator. Modules remain in stored array order but are grouped under every pergola, including an empty pergola left by Move, and their computed identity is `Pergola N · Module N` using the module's local ordinal inside that pergola. Staff can replace each default pergola label with a job-specific name; that name follows the pergola into the saved estimate, price breakdown, and quote line description. Rows show style, dimensions, active state, and validation-error count. Add module and Add pergola create fresh defaults; Duplicate deep-copies the active module and regenerates flashing/infill IDs; Move changes only `pergolaId`; Remove updates the browser draft immediately without an action-level confirmation and still protects the final structural module. Infill deletion follows the same immediate draft pattern and offers a short Undo action. No removal updates the estimate until Save, where the existing save confirmation and validation preflight remain the single modal decision point. Common starting templates replace the active module immediately after staff choose a template and press Apply to active module; the deliberate select-and-apply sequence supplies intent without another modal. The pergola name and site-level allowances remain unchanged. The navigator is a sticky rail at calculator widths of 1080px and above and an accessible modal launcher below that width. These actions do not reorder modules or change costing, estimate versioning, or automatic persistence semantics.

Calculator result freshness is explicit. Only a result produced from the current serialized costing request is `Live` and saveable. The debounced request lifecycle belongs to `useCalculatorCostingRequest`: an input change aborts the obsolete request, a late aborted response cannot replace the newest result, and a network/server failure retains the last valid result. While inputs are invalid, awaiting recalculation, or affected by a costing error, the last successful totals and drawings remain visible for continuity but are labelled `Last valid result`; Quote Status and save preflight continue to block until the result is current. This controller changes request ownership only: the authenticated costing API and `@sp/costing` remain authoritative for the result. At narrow calculator widths the form and preview stack under one page-owned scrollbar; the split, independently scrollable workspace remains at widths of 1080px and above.

Calculator configuration section order, Basic/Advanced visibility, and field-width presentation live outside `CalculatorGridClient` in the configuration-section model and form presenter. Field dependencies and validation IDs are unchanged. The two-column configuration workspace keeps module navigation as one structural owner and groups templates plus the complete configuration form in one main-column stack; new controls must join the appropriate stack or declare their grid ownership rather than relying on auto-placement. Templates and the Advanced Flashings grid respond to their own available container width before they can widen or be clipped by the configuration pane. Consecutive ordinary sections share quiet sheets with subtle dividers, while Blinds and Infills remain separate configuration cards. Labels and input-like toggles use a consistent control rhythm; routine field helper subtext is not rendered, while validation errors remain attached to their fields and visible. Automatic Roof pitch and Downpipes inputs add one presentation-only cue sourced from the selected authoritative result: current output says what Auto uses, retained output says what the last valid result used, and waiting output makes no numeric claim. Raw blank pitch and downpipe `0` are not rewritten; explicit values get no Auto cue; errors temporarily replace the cue in `aria-describedby`. Drainage controls and issue routing use the full `Downpipe joins` and `Downpipe elbows` labels without changing `downpipeJoinCount` or `downpipeElbowCount`. The responsive field grid deliberately renders three columns at the 1600px and 1024px browser checks, and two columns at 1366px and 768px, with one column on narrower mobile widths. Specialist Flashings, Blinds, and Infills controls use the full section width. The presentation-only Orientation diagram is omitted. The narrow command bar keeps Save prominent while retaining project/module identity, browser-draft explanation, readiness, and Basic/Advanced controls.

Calculator money labels distinguish internal costing from customer-facing values. The pricing preview's primary figure is the complete customer total produced by summing the same cent-accurate sell lines used at quote handoff: each pergola, shared site costs, valid blinds, and preserved legacy lighting. The saved `quoteDiscountPct` applies only to pergola and shared-site sell lines; blinds and lighting remain at list price. Exactly one persistent customer summary is visible for each layout: the Result Inspector header in the split workspace and the early result card in the stacked workspace. Both inc-GST and ex-GST values are explicitly labelled as rounded to the nearest whole dollar. The Pricing panel does not repeat that total; it carries the undiscounted exact-cent context and discount scope, unpriced-item qualification, permission-gated internal-cost disclosure, and exact-cent `Price by item` table with a matching footer total. Invalid blinds appear as unpriced, are excluded from the partial displayed total, and remain Save/quote blockers. Blind base/fabric pricing receives its shared `1.15x` core uplift before GST; the fixed `$900 inc GST` motor and width-priced roll-cover options (`No cover`, `$44/m inc GST` flashing, `$145/m inc GST` pelmet) are not uplifted. The calculator labels the vertical dimension `Blind drop` to distinguish it from the roll cover. Saved snapshots missing `rollCover` normalize to No cover without a schema or database migration.

The desktop preview rail is a tabbed Result Inspector. Its header keeps the current or last-valid customer price, freshness, input-issue count, and quote readiness visible while Pricing, Materials, Labour, Workings, and Issues route the existing output owners. Pricing contains pricing context, exact-cent price-by-item, permitted actual-cost review, and admin cost-impact surfaces without repeating the rounded lead total. Materials consumes the whole-job `@sp/costing` trusted breakdown: all BOM rows remain grouped by user-facing purpose and show quantity, unit, scope ownership, profile, assumptions, and supported stock/sheet `Why this quantity?` disclosures. Labour retains its existing admin and Advanced gates and preserves every work-stage activity, quantity, unit, minute, crew-hour, non-neutral loading, owner, internal cost, and calculated explanation. Each Materials/Labour group is a native disclosure keyed by its stable package group ID; the first starts open, the rest start closed, and user choices survive current/retained rerenders while the panel remains mounted. ## Estimate Pricing Rollout Boundary

Saved estimate pricing stays on the calculator path. The 2026-06-11 workbench breakaway disables workbench repricing rather than adapting object-first geometry back into calculator inputs.
